# End-to-End Kubernetes Monitoring and Observability on AWS EKS

## Project Overview

This project demonstrates the deployment of an end-to-end Kubernetes monitoring and observability solution on Amazon Elastic Kubernetes Service (EKS).

The monitoring platform uses Prometheus, Grafana, Alertmanager and the Prometheus Operator to collect, visualize and manage Kubernetes metrics and alerts.

Slack is integrated with Alertmanager to deliver real-time monitoring notifications to a dedicated Slack channel.

The project demonstrates practical Cloud Infrastructure and DevOps skills, including AWS infrastructure provisioning, Kubernetes administration, Helm deployments, metrics collection, dashboard visualization, alert configuration, notification integration and troubleshooting.

## Project Objectives

- Provision a managed Kubernetes cluster using Amazon EKS.
- Deploy a Kubernetes monitoring stack using Helm.
- Collect infrastructure and Kubernetes metrics using Prometheus.
- Visualize monitoring data using Grafana.
- Configure Alertmanager for alert processing and notification delivery.
- Integrate Slack for monitoring notifications.
- Test alert generation and notification delivery.
- Troubleshoot monitoring and notification failures.
- Understand the monitoring considerations and limitations of managed Kubernetes environments.

### Monitoring Workflow

1. Prometheus discovers and collects available Kubernetes and infrastructure metrics.
2. Node Exporter provides host-level metrics.
3. Kube State Metrics exposes Kubernetes object and resource-state information.
4. Prometheus evaluates monitoring and alerting rules.
5. Alertmanager processes notifications generated by Prometheus.
6. Alertmanager sends notifications to the configured Slack channel.
7. Grafana visualizes the collected metrics through monitoring dashboards.

## 1. AWS Infrastructure

The monitoring environment was provisioned using Amazon EKS and `eksctl`.

### Cluster Configuration

| Configuration | Value |
|---|---|
| Cloud Provider | AWS |
| Kubernetes Service | Amazon EKS |
| Cluster Name | `monitoring-cluster` |
| AWS Region | `us-east-1` |
| Kubernetes Version | `1.37` |
| Managed Node Group | `monitoring-workers` |
| Instance Type | `t3.large` |
| Desired Worker Nodes | 1 |
| Minimum Worker Nodes | 1 |
| Maximum Worker Nodes | 1 |
| Worker Volume Size | 30 GB |
| Availability Zones | `us-east-1a`, `us-east-1b` |
| Networking | Public subnets |
| Public API Access | Enabled |
| Private API Access | Disabled |
| SSH Access to Nodes | Disabled |
| Pod IMDS Access | Disabled |

The cluster was configured with two public subnets across separate Availability Zones.

A single managed worker node was used for the monitoring workloads.

### EKS Cluster Configuration

The infrastructure configuration is maintained in:

```text
monitoring-observability/
└── cluster.yaml
```

The configuration uses the `eksctl.io/v1alpha5` ClusterConfig format.

The deployment includes:

- A managed EKS node group.
- A `t3.large` worker instance.
- A 30 GB worker volume.
- Public API endpoint access.
- Restricted API access through an authorized client IP allowlist.
- Disabled SSH access to worker nodes.
- Disabled pod access to EC2 instance metadata.

The actual subnet IDs and authorized client IP are intentionally excluded from this public documentation.

### Provision the EKS Cluster

```bash
eksctl create cluster -f cluster.yaml
```

### Verify the Cluster

```bash
eksctl get cluster --region us-east-1
```

### Configure kubectl

```bash
aws eks update-kubeconfig \
  --region us-east-1 \
  --name monitoring-cluster
```

### Verify Kubernetes Connectivity

```bash
kubectl get nodes
```

The cluster uses public API access restricted to an authorized IP address. If the administrator's public IP changes, the allowlist must be updated before connecting.

### Notification Testing

A temporary PrometheusRule was created to test the notification pipeline.

Test alert:

```yaml
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: slack-integration-test
  namespace: monitoring
  labels:
    release: monitoring
spec:
  groups:
    - name: slack-integration-test
      rules:
        - alert: SlackIntegrationTest
          expr: vector(1)
          for: 0m
          labels:
            namespace: monitoring
            severity: warning
          annotations:
            description: Testing Kubernetes Prometheus and Alertmanager Slack integration.
```

The rule generated notifications through Prometheus and Alertmanager.

### Slack Webhook Troubleshooting

During testing, Alertmanager initially failed to deliver notifications to Slack.

Investigation showed that the webhook endpoint returned:

```text
HTTP/2 302
location: https://api.slack.com/
```

This indicated that the configured webhook endpoint was not accepting incoming webhook messages.

A new Slack Incoming Webhook was generated and connected to the correct channel.

The Kubernetes Secret was updated with the new webhook URL, and Alertmanager was restarted.

The updated integration successfully delivered notifications to Slack.

### Update the Kubernetes Secret

The webhook was updated without exposing its value in the terminal output.

```bash
read -s -p "Paste your NEW Slack webhook URL: " WEBHOOK_URL
echo

kubectl create secret generic alertmanager-slack-webhook \
  -n monitoring \
  --from-literal=slack-webhook-url="$WEBHOOK_URL" \
  --dry-run=client -o yaml | kubectl apply -f -

unset WEBHOOK_URL
```

### Restart Alertmanager

  -n monitoring

## 8. Alerting and Monitoring Rules

The deployment includes Prometheus alerting rules supplied by the kube-prometheus-stack.

Examples observed during the project include:

| Alert | Purpose |
|---|---|
| `Watchdog` | Monitoring pipeline heartbeat |
| `AlertmanagerFailedToSendAlerts` | Detects Alertmanager notification delivery failures |
| `AlertmanagerClusterFailedToSendAlerts` | Detects notification failures across the Alertmanager cluster |
| `KubeControllerManagerDown` | Monitors controller-manager scrape availability |
| `KubeSchedulerDown` | Monitors scheduler scrape availability |

### Managed Kubernetes Consideration

During final verification, the following alerts remained active:

```text
KubeControllerManagerDown
KubeSchedulerDown
```

Amazon EKS manages the Kubernetes control plane. Its control-plane components are not necessarily directly scrapeable by in-cluster Prometheus through the same endpoints available in self-managed Kubernetes clusters.

These alerts therefore represent a control-plane monitoring limitation that requires separate investigation and configuration for the managed EKS environment.

They were not treated as resolved.

The `Watchdog` alert remained active as the expected monitoring heartbeat.

## 11. Security Considerations

The project incorporates several security practices:

1. Slack webhook credentials are stored in a Kubernetes Secret.
2. Secret values are excluded from GitHub documentation.
3. Grafana, Prometheus and Alertmanager are accessed through port forwarding rather than public LoadBalancer services.
4. Monitoring components are deployed in a dedicated namespace.
5. Resource requests and limits are configured for monitoring workloads.
6. Public Kubernetes API access is restricted through an authorized IP allowlist.
7. SSH access to worker nodes is disabled.
8. Pod access to EC2 instance metadata is disabled.
9. AWS access is managed through the school's IAM Identity Center environment.

### Recommended Production Improvements

For a production deployment, additional improvements would include:

- AWS Secrets Manager integration.
- Kubernetes RBAC hardening.
- Network policies.
- Persistent monitoring storage.
- TLS-secured access to monitoring interfaces.
- Centralized audit logging.
- Highly available monitoring components.
- Regular backup and recovery testing.

## 12. Infrastructure Limitations

This project was deployed as a practical learning and portfolio environment.

The following limitations should be considered:

- One EKS worker node was used.
- Monitoring data retention was limited to three days.
- Persistent storage was disabled for the monitoring components.
- Grafana, Prometheus and Alertmanager were accessed through port forwarding.
- EKS control-plane metrics were not fully available to the in-cluster Prometheus configuration.
- The deployment was not designed as a highly available production monitoring environment.

Because persistent storage was disabled, monitoring data is not guaranteed to survive pod replacement or cluster recreation.

## 13. AWS Cost Management

The project uses Amazon EKS and an EC2 worker node, both of which can generate ongoing charges.

Important cost considerations include:

- EKS cluster control-plane charges.
- EC2 worker-node charges.
- EBS storage charges.
- Any additional AWS resources provisioned during deployment.

The cluster should be deleted after project verification and documentation are complete to prevent unnecessary ongoing costs.

### Delete the EKS Cluster

Only execute this command when the project environment is no longer needed:

```bash
eksctl delete cluster \
  --name monitoring-cluster \
  --region us-east-1
```

Verify that the cluster has been removed:

```bash
aws eks list-clusters --region us-east-1
```

Also verify that associated worker nodes, storage and CloudFormation resources have been cleaned up.

**Important:** Do not delete the cluster until all required project documentation and submission work is complete.
